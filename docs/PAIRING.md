# 四位随机码首次配对

## 旧方案与新方案

旧版本使用编译时固定的32字符共享密钥，电脑配置相同值；AUT1直接发送该值。旧代码已保存到固件4ecd502、电脑端b6c4480两份中文提交。本轮删除固定密钥验证，不保留自动降级入口。

新方案：S3 列出电脑与状态 → 点击电脑 → 首次自动显示 PIN 并在电脑弹窗 → 验证后自动串流。下一次连接通过新随机挑战自动双向验证，不再输入四位码。体验参考 Moonlight，协议仍为自定义 JPEG，不能与 Sunshine 互配。

四位码用 ESP32-S3 硬件随机源生成，保留0000等前导零，仅驻留内存，两分钟过期、最多五次尝试。重新开启需触屏操作；网络不能开启窗口。首次使用 SRP-6a 的2048-bit组和SHA256，避免直接发送四位码或采用可通过抓包穷举四位码的普通PIN-HMAC方案。应用层证明和凭据派生见 PROTOCOL.md；实现未经独立密码学审计。

S3 最多保存四台电脑的独立授权，NVS命名空间ms3pair/key peers（版本2表）；旧单条 peer 自动读入，原有授权继续有效。电脑使用稳定 computer_id，并按完整12位S3 ID保存独立凭据。配对前已绑定所选电脑ID，其他电脑不能抢用这个PIN窗口。

## 使用

1. 两端在同一局域网，电脑软件保持打开。
2. S3 首页列出电脑；已配对点选直接串流，首次需要配对则自动显示PIN。
3. 电脑自动弹窗，输入屏上四位数字，成功后自动开始；无需手动点电脑上的配对按钮，也没有长密钥输入框。
4. BACK返回电脑列表。查看/删除统一在两端的“已配对设备”；任一端删除后，下次自动重新配对。
5. 正常上传保留NVS；整片擦除或从0写完整factory可能清除授权及Wi-Fi设置。

旧config_secrets.h中的MOONLIGHT_PAIRING_TOKEN即使保留也不再参与编译验证，离线镜像检查会确认其值未嵌入应用。电脑旧顶层token字段不迁移为新授权；新settings.json只按pairings映射存储凭据。源代码目录和打包目录分别保存本地配置，不要将settings.json提交Git。

## 范围

四位码只用于短时物理授权；不是长期密码。已知电脑的长期凭据存于本机文件/NVS，当前未使用DPAPI、NVS加密或Flash加密。JPEG、触摸报文仍未加密和认证，不能等同Moonlight完整安全传输；仅用于可信局域网。配对实现依据 [RFC5054](https://www.rfc-editor.org/rfc/rfc5054) 的SRP计算和组参数，使用自定义应用证明，不是TLS-SRP。

## 自动验证的原理与防重放边界

首次输入的四位 PIN 只用来授权这次配对，不会一直充当登录密码。SRP 配对成功后，双方从本次会话秘密派生一个128-bit长期密钥，编码成32个十六进制字符保存。设备在NVS、电脑在本地settings.json保存各自那一份；正常后续认证不发送这个密钥。

每次自动连接的过程：

1. 电脑先报自己的完整身份ID。
2. S3从硬件随机源生成新的32-byte（256-bit）nonce，发给电脑。nonce是本次题目，可以公开。
3. 电脑计算 `HMAC-SHA256(K, "client" || 设备ID || 电脑ID || nonce)`，只把这个证明发回。K是保存的长期密钥。
4. S3用自己保存的K计算并对比；正确才放行。同时S3计算带 `"server"` 标签的证明，电脑也验证S3持有相同密钥。
5. 当前连接的挑战只允许验证一次，断线清除状态。下次连接产生新nonce；设备重启后也重新取随机数，不依赖会复位的时间戳或计数器。

所以“自动验证”的意思是双方自动证明还持有配对时保存的秘密，不是跳过验证，也不是每次传一遍长期密码。HMAC是带密钥的认证运算，不是把nonce简单做哈希；不知道K，只有抓到的nonce和旧证明，不能为新的nonce生成有效证明。

抓包后重放之前的认证证明，在新的nonce下不能通过。在合理的随机源和长期密钥未泄露的前提下，这能阻止被动抓包者通过复制旧登录报文冒充已配对电脑。之前的实机检查已记录 `fresh_nonce=true` 和 `old_client_proof_rejected=true`（performance/pairing-security.json）；该记录属于当时的实机版本。当前源码的挑战与证明公式保持一致，另有软件测试覆盖错误和重放证明。

| 情况 | 当前保护范围 |
|---|---|
| 抓取一次成功认证，再原样用于下一次连接 | 新随机挑战使旧证明失效 |
| 只监听认证过程，尝试直接读出长期密钥 | 认证报文不发送长期密钥 |
| 抓取JPEG画面或触摸内容 | 尚未加密，内容可能被读取 |
| 主动中间人实时转发认证，继而修改流量 | 当前认证没有和加密数据通道绑定，不能据此防护 |
| 对视频/触控业务报文做恶意修改或重放 | 尚未建立逐报文的密码学认证与防重放机制；CRC不等同HMAC |
| 直接读取电脑settings.json或设备NVS | 当前没有加密存储；取得长期密钥后可以冒充对应已配对端 |

因此准确结论是“认证握手具备防旧报文重放能力”，而不是“所有抓包、窃听、中间人和数据重放都能防”。若以后要保护完整串流，应加入认证加密通道，并把配对身份与该通道绑定。

参考：[RFC2104：HMAC](https://www.rfc-editor.org/rfc/rfc2104.html)、[RFC5054：SRP](https://www.rfc-editor.org/rfc/rfc5054)。本项目使用SHA256及自定义应用层证明，不是直接实现TLS-SRP。


## DHCP地址变化后的授权保留

固定设备ID与长期凭据不随IP变化。电脑端已修复“手填旧地址覆盖自动发现结果”的问题：空闲发现并验证设备签名后更新端点，电脑开始前也按完整ID重新定位，保留现有授权。换地址不能直接判定为未配对。只有删除/丢失凭据等真正的授权变化才重新输入PIN。

本轮只改电脑软件，不改动S3固件或Wi-Fi配置。实机保留旧IP40，自动定位同ID的新IP8并免PIN认证通过；48项测试包括双端UDP地址迁移、身份/签名验证、取消连接、配置写入失败及Windows单实例。原开发目录与运行目录存在不同的旧授权状态，本机保留已通过S3认证的运行版记录；不把失效记录覆盖回有效配置。


2026-10-30 地址恢复最终验收：新版自动更新并保存设备IP，原电脑身份与配对密钥保持一致；打包GUI检查退出码0，二次启动只激活原窗口。用户实际重启S3后确认仍可直接串流，无需手填IP或再次输入PIN。原始摘要见固件 docs/performance/address-recovery.json。本轮48项测试通过，未改动/烧录固件，未重测性能。


## 当前 v3 会话及存储更新

首次 SRP PIN 与长期证明公式维持 v2；后续入口改为 AU3? 并携带屏上当前请求ID，取消或过期后拒绝旧请求。PC PIN弹窗取消会反馈至S3。详细状态、消息及认证边界见 PROTOCOL.md。PC配置迁移至固定LocalAppData目录；S3配置迁移至64KB独立ms3_store分区，避免历史其他项目写满共享NVS。删除保存写回核对；空配对表在重启后优先于旧备份，不会恢复已删除授权。最终用户已确认删除、取消、重试配对正常，重启签名发现也通过。详见 SESSION_UX.md。
